# 第 0 阶段实测记录

## gRPC 连通（Task 1）
- `getStatus` 正常：模拟器 32.1.14，`hypervisorType: HVF`，`booted: true`。
- `sendKey({eventType:"keypress", key:"GoHome"})` 生效。
- `sendKey({eventType:"keypress", text:"中文abc"})` 在 Google 搜索框里只得到 `-abc`：**中文被丢弃**。结论：非 ASCII 必须走剪贴板（与设计 6.2 一致）。

## 画面传输实测（Task 3 / 4）

测试方法：
- 独立配置的 Chrome 157（`spike/drive-chrome.ts`，关闭后台节流）+ `spike/bench.html` 自动测速：8 次上下滑动开关应用抽屉统计帧率；10 次点击 Messages 图标，统计“按下 → 画面变化”延迟中位数。CPU 为同期 `ps` 每秒采样均值。
- 浏览器面板隐藏时页面被降频，最初一轮页面侧数据作废；分支会话在 15:20 前后也在同一台模拟器上测试，那段时间的数据作废。

**半分辨率 540×1170（Retina 上会糊，用户指出）**

| 模式 | 拖动 fps | 点击延迟中位数 | qemu CPU | 网关 CPU |
|---|---|---|---|---|
| rgba | 57 | 29ms | 127% | 32% |
| rgba-mmap | 56 | 20ms | 113% | 22% |
| jpeg | 46 | 21ms | 123% | 47% |
| png | 23 | 134ms | 172% | 3% |

**原始分辨率 1080×2340（画布 CSS 540×1170 × DPR 2）**

| 模式 | 拖动 fps | 点击延迟中位数 | qemu CPU | 网关 CPU |
|---|---|---|---|---|
| rgba | 47 | 22ms | 173% | 85% |
| rgba-mmap | 46 | 28ms | 124% | 36% |
| jpeg | 47 | 20ms | 195% | 139% |

**scrcpy 基线（1080×2340，H.264；adb `input swipe` 驱动滑动）**：每秒 33–67 帧，qemu 156% + scrcpy 3.6%。点击延迟基线未测（需录屏，未征得同意）。

**同口径对照（adb 滑动，网关直取 RGBA 540×1170，不经浏览器）**：每秒 45–59 帧，模拟器 → 网关约 10ms，qemu 98% + 网关 13%。

其他发现：
- 模拟器 32.1.14 的 RGBA 帧是自上而下的行序，与 proto 注释“bottom up”相反。
- 画面不变时模拟器不推帧（空闲时每秒 0 帧）。
- 页面断开后 gRPC 流会被取消（日志 8 次 `stream cancelled`），但网关空闲 CPU 是 1.2–2.1%，没到计划要求的 1% 以下（推测是 2ms 轮询或 gRPC 保活，第 1 阶段改掉）。

## nsh 嵌入验证（Task 5）

环境：本机构建的 nsh，`ui/`（TSX + `host.js`），宿主模块用 rgba-mmap、按 DPR 取帧。验证脚本 `spike/check-nsh.ts`：独立 Chrome，CDP 真实鼠标和键盘事件。开发模式（`nsh run --target web --port 8796`）和打包产物（`nsh package --target web`，本机 `http.server` 托管）结果一致：

| 项 | 结果 |
|---|---|
| (a) `web.host` 生效 | 通过：canvas 在 `[data-testid=screen]` 内，画面在更新；“主页”按钮经 `host.call("emu.key")` 让模拟器从设置页回到桌面 |
| (b) 重新渲染后画布还在 | 通过：连续切换 20 次（兄弟节点出现和消失、占位 View 背景色变化），canvas 0 次丢失、0 次重新挂载，之后画面照常更新（72 帧） |
| (c) 键盘焦点 | 通过：点击画布后，`a` / `Enter` / `Backspace` 三个 keydown 都到了 canvas；Cmd+R 默认行为没被阻止（用合成事件检查） |
| (d) CSP | 通过：无 CSP 报错。打包产物的 `connect-src` 由 `web.connect` 自动生成为 `'self' http(s)://127.0.0.1:* ws(s)://127.0.0.1:* http(s)://localhost:* ws(s)://localhost:*`，带协议和端口通配 |
| 公网 https 页面 + Chrome 本地网络权限 | **未验证**：需要对外上传，等用户同意 |

注意：`nsh run` 在整台机器上同一时间只有一个开发会话，`--port` 也会替换之前的会话。这次把本机 :8790 上另一个项目的 nsh 开发服务器顶掉了。以后在本机开发这个项目时，要避开其他 nsh 项目正在开发的时段，或者只用 `nsh package` 加静态托管。

## 统一口径复测（审查之后，`spike/measure.ts`，结论以此为准）

审查指出：前面的 CPU 采样包含空闲期，用的 `ps %cpu` 是衰减平均；fps 的分母里有等待时间；scrcpy 用的是另一种滑动方式。这些都让前后数据无法直接比较，所以全部重测。

| 目标（1080×2340） | 每秒帧数（逐秒） | 中位数 | 点击 p50 / p90（n=30） | CPU qemu / 网关 / 显示端 |
|---|---|---|---|---|
| scrcpy | 39,60,60,60,60,60,53 | 60 | 未测 | 203% / – / 5% |
| page:rgba-mmap | 62,60,60,60,59 | 60 | 20 / 30ms | 136% / 69% / 52% |
| page:rgba | 50,51,55,56,55 | 55 | 21 / 43ms | 177% / 108% / 52% |
| page:jpeg | 44,47,48,46,48 | 47 | 19 / 33ms | 158% / 143% / 42% |

scrcpy 的 `--print-fps` 输出写文件时有缓冲，脚本当场读不到。上表里 scrcpy 的逐秒帧数是事后从完整日志里取的。

结论：选 rgba-mmap。前面“原始分辨率下都不达标”的判断是口径问题导致的，作废。

## 第 1 阶段正式页面复测（Task 5，`spike/measure.ts` 目标 `app`）

口径同上：同一组 16 次上下滑动（每步 16ms），只算滑动窗口内的 CPU 时间增量（qemu + 网关 + 本脚本起的 Chrome 全部进程），每个目标前冷却 20s。改动：页面目标换成正式页面 `http://127.0.0.1:7300/`（`pnpm start`），滑动由 CDP 真实鼠标事件在画布上发出；帧率取宿主模块每秒一行的 `console.debug`（`fps` = 绘制次数），只取完整落在滑动窗口里的秒；视口覆盖成 760×1260、DPR 2，取帧 1080×2340。正式页面没有点击延迟钩子，这次不测点击。

本机当时负载偏高（load average 约 9，后台有一个进程常驻 100% 和一个 iOS 模拟器），所以同时重测了 scrcpy。

| 目标（1080×2340） | 每秒帧数（逐秒） | 中位数 | CPU qemu / 网关 / 显示端 | 合计 |
|---|---|---|---|---|
| scrcpy（本次） | 26,51,48,47,51,46,47（事后从日志取） | 47 | 160% / – / 4% | 164% |
| app 第 1 次 | 49,50,52,52,51,51,43 | 51 | 107% / 53% / 53% | 213% |
| app 第 2 次 | 60,59,60,60,61,59,60 | 60 | 115% / 64% / 57% | 236% |
| app 第 3 次 | 60,60,59,59,60,60,58 | 60 | 121% / 64% / 58% | 243% |

（网关带 `DEBUG=1` 时另跑过 3 次：中位数 58 / 54 / 50，合计 CPU 259% / 233% / 235%。）

判定：帧率中位数 51–60，满足“不低于 50”，但第 1 次只高出 1 帧，有余量不足的风险。CPU 合计 213–243%，是第 0 阶段 scrcpy 基线 208% 的 1.02–1.17 倍；按本次负载下重测的 scrcpy 164% 算是 1.30–1.48 倍。两种算法都不超过 1.5 倍。
